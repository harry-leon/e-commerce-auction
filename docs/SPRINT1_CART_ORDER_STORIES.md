# Sprint 1 cart and order stories — draft for BA review

Owner in the sprint plan: Linh Đang. This is a proposed backlog, not a record of stakeholder acceptance. Reconcile with SRS business configuration, payment/shipping providers and the team Definition of Done before estimation.

| ID | User story | Acceptance criteria |
| --- | --- | --- |
| CART-01 | As a buyer, I want to add a SKU to my cart so I can purchase the correct variant. | Given an active product/SKU, adding a positive quantity creates or updates one cart line for that SKU. Inactive/deleted SKUs and invalid quantities are rejected without changing the cart. Product, SKU, price and quantity are displayed. |
| CART-02 | As a buyer, I want to change quantities and remove lines. | Quantity changes revalidate current availability. Removing a line updates totals. Removing the last line shows an empty cart. Another user's cart cannot be read or modified. |
| CART-03 | As a returning buyer, I want my guest cart merged when signing in. | When guest carts and merge are enabled by business configuration, merge combines identical SKUs, revalidates quantities and reports unavailable items. Retrying the merge does not duplicate lines. Expired guest carts follow configured expiration behavior. |
| CHECKOUT-01 | As a buyer, I want to confirm current prices and shipping details before placing an order. | Checkout revalidates price, product/SKU status, quantity and availability on the server. Changed prices or unavailable items are shown before final confirmation. Shipping address is required for physical goods; digital delivery follows the SRS. Currency, subtotal, shipping, applicable discounts/tax and payable total are shown consistently. |
| ORDER-01 | As a buyer, I want one order for a confirmed checkout even when I retry. | The request carries an idempotency key. Same key and same payload return the original order; reusing the key with different content is rejected. Concurrent retries cannot create duplicate orders or inventory reservations. Order lines retain a snapshot of purchased SKU descriptions and prices. |
| PAYMENT-01 | As a buyer, I want payment results to update my order reliably. | Only verified provider callbacks can change payment state. Duplicate callbacks are idempotent. Failed/expired payments follow configured timeout and reservation-release rules. The browser redirect cannot independently mark an order paid. Exact status transitions require backend/BA review. |
| ORDER-02 | As a buyer, I want to view my order history and details. | History is paginated and ordered by creation time. Detail includes purchased items, totals, shipping information and current order/payment status. Only the owning buyer and authorized staff can access it. Empty, loading and failure states are visible. |
| ORDER-03 | As a buyer, I want to cancel an eligible order. | Server checks the allowed cancellation window and current state against the SRS. An accepted cancellation is recorded once, releases eligible inventory and starts any required refund process. A repeated request does not duplicate releases/refunds. Disallowed cancellation returns a clear reason. |

Required integration tests: duplicate checkout/callback, concurrent stock reservation, price change between cart and checkout, expired checkout, cross-user access denial, payment failure and inventory release. Provider sandbox credentials and final refund/status rules must be supplied or approved by the team.
